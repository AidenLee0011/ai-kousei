## 測ってみたら、差ははっきりしていた

LLM に日本語のコミットメッセージを書かせると、ほぼ必ずこうなります。

```
feat: 商品詳細APIにRedisキャッシュを追加

商品詳細APIの応答速度向上とデータベース負荷軽減のため、Redisキャッシュを導入しました。
キャッシュの有効期限（TTL）は300秒に設定されています。
```

一方、日本語話者が書いたコミットはこうです。

```
fix: 商品詳細APIにRedisキャッシュを追加

なぜ: 商品詳細APIの応答が遅く、DB負荷も高い
なにを: Redis を前段に追加。TTL 300秒
確認: p95 820ms → 210ms
```

印象の問題ではなく、数えられる差です。GitHub から 2022 年 11 月以前（チャット LLM が普及する前）の日本語コミット 96 件を集め、同じ変更内容を LLM に書かせた 30 件と比べました。

| 指標 | 人手コミット 96 件 | LLM 生成 30 件 |
|---|---:|---:|
| 本文が敬体（です・ます体） | 1.0% | **83.3%** |
| 常体と敬体の混在 | 1.0% | 80.0% |
| 一文 60 字超 | 2.1% | 33.3% |
| 受身形の多用 | 0.0% | 13.3% |

記録文書は常体か体言止めで書く、という慣習が数字に出ています。これは好みの話ではなく、[公用文作成の考え方（文化審議会建議）](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93651301_01.pdf) Ⅲ-1-ア に「文書の目的や相手に合わせ、常体と敬体を適切に選択する」と書かれている話です。

そこで、この差を条文を根拠に指摘するリンターを作りました。

- リポジトリ: https://github.com/AidenLee0011/ai-kousei
- ブラウザデモ（インストール不要）: https://aidenlee0011.github.io/ai-kousei/

## 使い方

Python でも Node でも動きます。依存パッケージはゼロ、モデル呼び出しもネットワークアクセスもありません。

```bash
pip install ai-kousei
ai-kousei hook install --lang ja     # commit-msg フックを入れる
```

```bash
npx ai-kousei lint report.md --profile report
```

生成文らしいコミットは、コミット前に止まります。

```
$ git commit -m "feat: 各種修正"
next: 対象と結果を書く。「決済リトライの上限を3回に変更」
日本語 / コミット・PR（記録）  score 88/100  errors 1  warnings 0  [blocked]
1. [ERROR] 件名だけでは内容がつかめない
     found: feat: 各種修正
     src:   公用文作成の考え方（文化審議会建議） Ⅲ-2-エ 文書の構成
     rule:  ja-koyo-vague-heading
```

指摘には必ず**条番号と原文の引用**が付きます。何を根拠に指摘されたのかが分かるので、直すかどうかを自分で判断できます。

## 用途によって、正解は反転する

同じ「です・ます体」が、記録では誤りで、対顧客では必須です。だから用途を推測せず `--profile` で明示します。

| プロファイル | 対象 | 主な検査 |
|---|---|---|
| `commit` | コミット・PR | 常体・体言止め、件名で内容がつかめるか |
| `report` | 社内報告書 | 見出し階層（第1 → 1 → （1） → ア）、文体の統一 |
| `agent` | エージェント間の受け渡し | 曖昧語の禁止（適宜・随時・必要に応じて）、動作主の明示 |
| `customer` | 対顧客の文面 | **敬体の強制**、社内用語の言い換え |

エージェント間の受け渡しは実際に効きます。

```
AS-IS  エラー時は適宜リトライし、必要に応じて通知する。
TO-BE  エラー時は最大3回・10秒間隔でリトライする。3回失敗したら Slack #ops へ通知する。
```

「適宜」は人間なら補完できますが、受け手が機械だと実行できません。公用文作成の考え方 Ⅲ-3-シ の「言葉の係り方によって複数の意味に取れることがないようにする」を、そのまま機械向けの規則にしています。

## 規則の根拠は全部たどれる

規則は 23 件、すべてが次のいずれかを条番号付きで引用しています。

| 出典 | 発行 |
|---|---|
| 公用文作成の考え方（文化審議会建議） | 文化審議会・2022-01-07 |
| JTF日本語標準スタイルガイド（翻訳用） | 日本翻訳連盟 |
| textlint-rule-preset-ja-technical-writing / preset-ai-writing | textlint-ja |
| 公開報告書コーパス（JPCERT/CC 活動報告 8 件・8,181 文） | 実測 |

引用が本物かどうかは、CI が毎回検査します。出典 18 件を実際にダウンロードし、規則が主張する引用文が原文に一字一句あるかを照合して、無ければビルドを落とします。

実は最初に走らせたとき、**私が書いた引用のうち 7 件が要約になっていて落ちました**。全部、原典の文へ差し替えてあります。この仕組みがないと、それらしい条番号を付けた作文が混ざります。

## 誤検出はどれくらいか

規則を増やすほど誤検出は増えます。なので、人が書いた本物の文章に対する発火率を測っています。

| 検査対象（すべて人が書いた文章） | プロファイル | error 発火 |
|---|---|---:|
| コミット 96 件（2022-11 以前） | commit | **2.1%** |
| 公開報告書の本文 400 ブロック（JPCERT/CC） | report | **2.2%** |
| 同じ報告書を、わざと誤ったプロファイルで検査 | commit | 96.8% |

形態素解析は使わず正規表現だけですが、用途に合ったプロファイルなら人の文章はほぼ素通りします。用途を取り違えると全部止まるので、`--profile` は明示する設計にしています。

## 限界

- 規則は 23 件です。textlint 系の網羅性には及びません。
- 形態素解析を使わないので、文脈依存の判定は苦手です。
- 日本語以外（韓国語・中国語・ドイツ語・フランス語・スペイン語）は初期版の規則だけで、出典の整備はこれからです。
- 英語は対象外です。英語向けは既存ツールが充実しています。

## 近いツールとの違い

「最初」でも「唯一」でもありません。日本語の AI 文体を扱うツールは既にあります。

| ツール | 対象 | ai-kousei との違い |
|---|---|---|
| [textlint-rule-preset-ai-writing](https://github.com/textlint-ja/textlint-rule-preset-ai-writing) | 散文の AI パターン | ai-kousei は指摘に条番号を出し、CI が原文と照合する |
| [textlint-rule-preset-JTF-style](https://github.com/textlint-ja/textlint-rule-preset-JTF-style) | JTF 表記規則 | 同 preset は JTF 2.1/2.2 版ベース。ai-kousei は 4.0 版（2026-07-25, CC BY 4.0）を引用 |
| [patina](https://github.com/devswha/patina) | KO/EN/ZH/JA の humanize | patina は書き換えまで行い commit-message 用の document type もある。ai-kousei は書き換えず、指摘と条文だけ出す |
| [humanizer-ja](https://github.com/gonta223/humanizer-ja) | 日本語 AI 文体 20 パターン | ai-kousei は CLI・フック・誤検出率の実測値を持つ |

違いは 3 点です。**根拠が条番号でたどれること**、**用途によって規則が反転すること**、**誤検出率を測って公開していること**。

## 作った理由

AI が書いた文章を直すための規則が作者の感覚で作られていると、直した結果が本当に自然なのかを誰も検証できません。
公的な文書規範という、すでに合意のある基準を機械可読にして、根拠を毎回提示する。それだけの道具です。

規則の追加は歓迎します。条件は 2 つで、出典（文書名・条番号・引用）と、AS-IS / TO-BE の書き換え例です。
